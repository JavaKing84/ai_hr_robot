## 二、三个根因与修复原理

### 1. 解析结果被误判超时（关键 bug）

**现象**：Boss 那份 8.7 MB / 3 页 PDF，直接用 pypdf 抽有 **4161 字符**，但走项目的子进程封装后 `resume_text=0`。

**实测基线**：

```
[直接同步解析] 0.94s  | engine=pypdf | chars=4163 | pages=3
[子进程-旧实现] 21.02s | ok=False | timed_out=True | exitcode=-15
```

明明算完了，却被强杀。

**原因**：旧代码 `run_in_subprocess()` 是

```python
process.start()
process.join(timeout)      # ← 先等进程退出
...
result_queue.get(timeout=5)  # ← 之后才取结果
```

`multiprocessing.Queue` 由子进程里的 **feeder 线程异步写管道**，子进程退出清理时要等 feeder 写完；
主进程在 `join()` 期间一直不读队列 → 子进程等主进程读、主进程等子进程退 → **互等**，
到点被 `terminate()`，结果作废，`service/ingestion.py` 按约定降级成空文本。
之前 14 KB 的 docx 能过、8.7 MB 的 Boss PDF 全挂，就是这个差异。

**修复**：把顺序倒过来 —— 主进程以 `timeout` 为总上限，**持续 `result_queue.get(0.05s)` 消费结果**，
同时轮询 `process.is_alive()` 和截止时间：

- 拿到结果 → 再 `process.join()` 收尾，子进程能正常退出；
- 进程提前退出（段错误 / OOM / `os._exit`）→ 只留 0.5s 给队列刷残留，随后快速按崩溃返回，不必空等满 60s；
- 到点仍无结果 → `terminate()` → `kill()`，返回 `timed_out=True`。

三种兜底（超时、崩溃、子进程内异常）全部保留。

**修复后**：`2.10s | ok=True | exitcode=0 | chars=4163`。

### 2. 平台统一发件人把后续简历全吞成「候选人回信」

**现象**：20 封 `cv@notice.zhipin.com` 的 Boss 通知，只有第 1 封落地，其余 9 封被判成 `candidate.reply.confirm`，附件根本没入库。

**原因**：第 1 封解析失败后，兜底逻辑把 `From` 写成了候选人字段 —— `name=BOSS直聘`、`email=cv@notice.zhipin.com`。
而 `email_threading.match()` 的兜底 4 是「按发件人邮箱找候选人」。
Boss 给**所有**候选人共用同一个通知发件人，于是之后每一封新简历都被认成「这位候选人的回信」。

**修复（三层）**：

1. `email_threading.match()`：带简历附件的邮件 → 直接返回 `unknown`，跳过「按发件人认人」兜底；
   **基于 `In-Reply-To` / `References` / `reply+token` 的线程匹配仍然保留**，真实回信照常处理。
2. `email_threading.match()`：平台通知地址（`noreply` / `notice` / `cv@` 等特征）一律不作为身份依据，
   顺手消掉无附件通知产生的 `candidate.reply.other` 噪声。
3. `inbound_email.handle_email()`：双保险 —— 带简历附件时，即使线程命中主管/候选人，也优先走新简历入库。

另外把三处重复的附件后缀白名单收敛成单一数据源 `RESUME_ATTACHMENT_SUFFIXES`。

### 3. 平台名被当成候选人姓名

`service/ingestion.py` 的 `_apply_contact_hint()` 修复：

- 平台地址不写 `extracted.email`；
- 平台显示名（`BOSS直聘` 等）不写 `extracted.name`；
- 姓名改从**邮件主题 / 附件名**兜底（`_guess_name()`）：Boss 主题
  `谷金玉 | 4年，应聘 python开发工程师 | 北京11-12K【BOSS直聘】` 和附件名
  `【python开发工程师_北京_11-12K】谷金玉_4年.pdf` 里都写着真名，比正则更便宜也更准
  （平台 PDF 正文里根本没有「姓名：」这种字段标签）。
- `_fallback_name()` 也加了同一层兜底。
