## 二、自查发现的问题（不在原清单里）

清单是别人看代码看出来的，以下五条是本轮**实测**撞出来的，都修了，也都有回归用例。

### 2.1 幂等判重每封信都要全表扫一次（本轮最值得说的一个）

`0003` 建的部分唯一索引谓词里带 `status`，而两条热路径的查询并不约束 `status`：

```python
# repository/message.py
find_delivered(external_id)   # 每发一封面试通知先查一次幂等键
seen_inbound(channel, external_id)  # 每条入站消息查一次
```

PostgreSQL **无法证明**查询行落在部分索引里，于是放弃索引 → `Seq Scan`。在 6 万条 `messages`
的压测库上实测：

| | 计划 | 耗时 |
|---|---|---|
| 修之前 | `Seq Scan on messages`（扫 60057 行） | **7.5 ms / 次** |
| 修之后 | `Index Scan using ix_messages_external_id` | **0.05 ms / 次** |

150 倍。这不是「偶尔慢一下」，是**每封信、每条入站消息各一次**，量一上来就是最贵的查询。

修法：`0004_message_lookup` 补一条不带 `status` 谓词的单列索引
`ix_messages_external_id (external_id) WHERE external_id <> ''`。唯一性仍归 `0003` 那条部分
唯一索引管，两者职责分开。回归用例 `test_idempotency_lookup_uses_index` 用
`EXPLAIN` 直接断言「不能出现 Seq Scan」。

> 为什么不用「给查询加 status 条件」的办法：`seen_inbound` 的语义是「这条入站消息处理过没有」，
> 一旦给查询加上状态白名单，某天冒出一个新状态就会**静默漏判**——宁可多一个索引，不要这种隐患。

### 2.2 401 走了 FastAPI 默认渲染，丢掉 `WWW-Authenticate`

`middlewares/exception.py` 里 `HTTPException` 被渲染成 `{"error":{"code":"http_401"}}`，
而且 `headers` 被丢掉（RFC 7235 要求 401 带 `WWW-Authenticate`）。改成状态码→可读 code 的映射表
（`unauthorized` / `forbidden` / `not_found` …），并把 `headers` 透传。用例：
`test_auth_error_uses_unified_envelope`。

### 2.3 排期「静默吞人」的残留分支

清单里的 P0-bug 是「点名的人被 filter 掉、不解释」。修的过程中发现还有一层：
模型和规则**都没抽出名字**时，`requested` 为空 → `missing` 也为空 → 主管收到的还是一句
通用格式提示，仍然不知道问题出在人的状态上。

补了 `_names_mentioned()`：模型抽不到时退一步在原文里找「确实存在于该主管名下职位」的人名
（长名字优先匹配，避免「张三丰」被「张三」抢走），再用 `_explain_unschedulable()` 逐人说明：

```text
这几位这次没能安排：
· 李四：筛选通过——该候选人已筛选通过但还没发给主管，无法排期
· 王五：已被判定不合适（已淘汰）
· 赵六：我这边没有这个人（请确认姓名或该候选人是否属于您名下职位）
```

部分成功时还会额外回一条 `feedback_partially_applied`，不让「排上了 2 个、漏了 1 个」看起来像全成功。

### 2.4 `/health` 看不到库版本

交接场景下第一个问题是「这个库是最新的吗」。`app.state.schema_revision` 早就有了，只是没暴露。
加到 `/health` 的 `components` 里，比 `alembic current` 快得多。

### 2.5 测试用例自己没测到目标行为

`test_failed_notice_keeps_status` 用 `session.flush()` 造数据，而 `services` 夹具拿的是**另一个连接**，
flush 的行它看不见 → 先撞 `email_threads` 外键，用例在「准备阶段」就红了，
真正想测的「发送失败不推进状态」根本没执行。改成 `commit()`（跟同文件另一条用例一致）。

> 这条值得记下来：**测试红了不一定是代码错，也可能是夹具没把数据交出去**。
> 如果当时图省事把断言删掉，就会留下一条「永远绿、但什么都没测」的用例。

## 三、索引重排：按真实查询改，并用 EXPLAIN 逐条验收

压测库：`hr_mig_test`，20024 候选人 / 60057 消息 / 80110 事件（结构与线上一致）。

### 删掉的（纯写放大）

14 个被复合索引前缀覆盖的单列索引，例如有了 `(status, position_code, id)` 之后
单独的 `(status)` 就是纯负担——每次写都要多维护一棵树，读却永远用不到它。

### 保留 / 新增的，逐条对得上代码

| 索引 | 服务的查询 | 实测计划 |
|---|---|---|
| `ix_candidates_status_position_id` (status, position_code, id) | 主管看自己名下的名单，按 id 翻页 | `Index Scan`，0.06 ms |
| `ix_candidates_position_status_score` (position_id, status, score) | 按职位取最高分发给主管 | `Bitmap Index Scan` |
| `ix_candidates_email` | 按邮箱判重投 | `Index Scan`，0.017 ms |
| `ix_candidates_cycle_id` (cycle_id, id) | 每日闭环取本轮候选人 | 取值稀疏时走索引；取值占全表 99% 时规划器自动改走 pkey（**正确决策**，不是 bug） |
| `ix_candidates_interview_time`（部分索引） | 按时间排面试 | `Index Scan`，0.095 ms |
| `ix_candidates_skills_gin`（jsonb_path_ops） | `skills @> '["PyTorch"]'` | `Bitmap Index Scan`，47 行 / 3.7 ms |
| `ux_messages_channel_external`（部分唯一） | 挡重复回调 | 已建，历史 25 条重复清成 1 条 |
| `ix_messages_external_id`（**本轮补**） | 幂等判重 | `Index Scan`，7.5 ms → 0.05 ms |
| `ix_messages_retry`（部分） | 失败补发 / 待确认扫描 | 索引可用；小表上规划器选 Seq Scan 更便宜，`enable_seqscan=off` 下确认能命中 |
| `ix_events_object` (object_type, object_id, id) | 「这个人为什么没过」溯源 | `Index Only Scan`，**Heap Fetches: 0**，0.11 ms |
| `ix_email_threads_message_ids_gin` | 按 Message-ID 归线程（回复串起来） | 已建 |

### 还没解决的索引缺口（写清楚，不装看不见）

`build_search` 里的姓名检索是 `name ILIKE '%张%'` —— 前置通配符 btree 用不上，实测 `Seq Scan`
6.5 ms / 2 万行。正解是 `pg_trgm` + GIN：

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;   -- PG13+ 是 trusted extension，库 owner 就能建
CREATE INDEX ix_candidates_name_trgm ON candidates USING gin (name gin_trgm_ops);
```

**这次没做**，理由：① 线上只有 24 条候选人，全扫 0.02 ms，加了是纯仪式；② 要在云端共享库上
装扩展，属于「动别人的环境」，应该先问一声再动。已经写在这里，谁需要谁执行一条 SQL 即可。

## 四、与五个开源项目的对比：这一轮把差距补到哪里

`开源项目对比-compare.md` 里给本项目列了 7 条技术缺点 + 5 条业务缺点，并建议「只能做三件事」。
这一轮做完了第 1 件、第 2 件，第 3 件做了一半。

### 4.1 原来 7 条技术缺点

| 原缺点 | 现状 | 说明 |
|---|---|---|
| 没有数据库迁移，改字段只能手工 ALTER | ✅ **已解决** | Alembic `0001`→`0004`；启动自动升级 + 咨询锁；`alembic check` 无漂移 |
| 没有外键与唯一约束，删候选人留孤儿 | ✅ **已解决** | 7 条外键（`ON DELETE SET NULL`）+ 消息部分唯一索引 |
| JSON 用 `json` 不是 `jsonb`，建不了 GIN | ✅ **已解决** | 12 列转 jsonb + 3 个 GIN |
| 定时任务是进程内 APScheduler，多实例重复跑 | ✅ **已解决** | PG 咨询锁互斥；但**仍是进程内调度**，没有独立 worker（见 4.3） |
| 文件存本机磁盘，换机即丢 | ⚠️ **缓解** | 已挂卷 `./var:/app/var`，容器重启不丢；但**跨机器仍不共享**，正解是对象存储 |
| 无可观测性，只有 JSON 日志和 events 表 | ✅ **已解决（最小版）** | `/ops/metrics` + `/ops/funnel` + `/stats`；没有 trace，也没有看板 |
| 扫描件无 OCR | ❌ **没做** | 需要 `unstructured[ocr]`（连带 torch ≈2GB），且要过「解析子进程 60s 超时」这关 |

### 4.2 逐项目：现在还能从它身上学什么

**Resume-Matcher（29k★，技术最像）**
它公开了 ATS 分的完整公式（关键词 40% / 技能 20% / 岗位名 15% / 章节完整 15% / 日期一致 10%），
纯代码可解释。本项目 `score_detail.hits` 记了命中项，但**没有对外表达**。
这轮做了 `/stats`，但**还没把「关键词覆盖率 / 章节完整度」这类纯规则指标做成可读字段**——
它是「HR 问『为什么 62 分』」时最低成本的答案来源。列为下一步。

**Dify（161k★，架构对标）**
- provider 抽象：本项目已是「每个供应商自带 base/key 的链 + 三供应商降级 + 全挂退回规则」，
  方向一致，规模小一个量级。
- 可观测性：Dify 有完整运行追踪。本项目补了 metrics 指标，但**没有单次运行的链路追踪**。
  现在排查「这封简历为什么没通过」仍需写 SQL（`/recruitment/candidates/{id}/events` 能看流水，
  但看不到 LLM 调用耗时/降级路径）。
- function calling：**仍是固定意图路由**（`service/agent.py` 的读写分类），不是工具调用。
  这是「Agent 能不能真对话」的分水岭，见 4.3。

**frappe/hrms（9k★，HR 域模型最完整）**
它的 Department / Designation / Employee 分层比本项目扁平的 `positions.yaml` 更抗组织变动
（一个部门多主管、主管换人只能改文件）。**这轮没动**：产品文档明确「不做人才库、不做管理员」，
组织主数据属于「有管理后台才需要」的东西，现在加反而是负债。等真出现「一个部门两个主管」的
需求再说，届时 `positions.yaml` 加一层 `teams` 即可，不动表结构。

**pyresparser（959★，已停更）**
这一层本项目已超过它（规则优先 + LLM 补位 + 子进程隔离 + 中文排版适配）。
唯一可抄的是它的**字段级置信度**：本项目只有整体 `confidence`，抽错姓名和抽错技能在库里长得一样。

**OpenCATS（782★，业务最像的传统 ATS）**
它的「报表/漏斗」是这轮补上的（`/stats` + `/ops/funnel`）。它的「人才库/复投」按产品文档
**明确不做**；本项目用 `is_duplicate` 标记重复投递，只用于「不重复打扰主管」，不用于沉淀人才池——
这是刻意的能力克制，不是缺口。

### 4.3 仍然缺的（诚实清单）

| 缺口 | 为什么这轮不做 | 真要做的做法 |
|---|---|---|
| 对象存储（简历/打包件） | 单机部署，挂卷够用；换 OSS/MinIO 要改 `core/paths.py` + 全部读写点 + 迁移历史文件 | 抽一个 `StorageClient` 接口（`put/get/exists`），先实现本地版与 MinIO 版，`resume_path` 存 key 不存路径 |
| 多租户 / 组织主数据 | 产品文档：单公司单 HR，不做管理员 | 先加 `tenant_id` 到 6 张表 + 全查询加过滤，代价大，须先有第二个客户 |
| 扫描件 OCR | `unstructured[ocr]` 连带 2GB 依赖，装完还得压进 60s 超时预算 | 单独进程 + 队列，异步补 OCR 后回写 `resume_text`，不阻塞当日闭环 |
| 飞书 function calling | 意图路由已覆盖高频问法（查名单/看统计/读简历），再往上要工具注册 + 权限边界 | 把现有 `ReportingService` / 候选人查询注册成 5~6 个工具，用模型决定调用；写操作仍走确定性代码 |
| 链路追踪 | 量太小，JSON 日志 + `events` 表够用 | 接入 OpenTelemetry，先把「一轮闭环」串成一条 trace |
| 姓名模糊检索 | 24 条数据，全扫 0.02 ms | `pg_trgm` + GIN（SQL 见第三节末尾） |

### 4.4 对比之下的真实位置

一句话：**业务纵深已经超过这五个项目里任何一个，工程化从「能跑」进到「敢上生产」，但离
「平台」还差一个数量级**。Dify 那种「可视化编排 + 多租户 + 插件市场」不是这个项目的目标，
产品文档把范围收在「HR 每天省 1~2 小时」这一件事上——按这个标准，现在该有的都有了。

## 六、云库同步（交接第一件事）

云端 `10.191.44.66:15432/hr_ai_robot` 已有 6 张业务表，但版本落后（`0002` 或更早）。
同步只有一条命令，脚本会自己把「备份 → 迁移 → 自证」走完：

```bash
cd D:\!pythonproject\hr_ai_robot

# ① 先体检（不改任何东西）
uv run python scripts/sync_db.py --check \
  --target postgresql://admin:<密码>@10.191.44.66:15432/hr_ai_robot

# ② 备份 + 迁移 + 逐条自证
uv run python scripts/sync_db.py \
  --target postgresql://admin:<密码>@10.191.44.66:15432/hr_ai_robot

# ③ 需要把本机 24 条真实数据也带过去（先清空云端 6 张表，语义是「两边一致」）
uv run python scripts/sync_db.py \
  --target postgresql://admin:<密码>@10.191.44.66:15432/hr_ai_robot --copy-data --yes
```

脚本的硬规则：

1. **目标库有数据就必须先备份成功**，备份失败直接退出（码 2），不给「先升了再说」的机会；
2. 迁移用 `alembic upgrade head`，URL 显式注入，不吃 `.env`；
3. 迁移完**逐条断言**：12 个 jsonb、19 个 timestamptz、10 个关键索引、`messages` 无重复
   `(channel, external_id)`、版本号 == head；任一不过就以非 0 退出，不会「看起来成功」；
4. 顺带产出 `var/db_backup/ddl/<库>_indexes_<host>.sql`，两端 diff 一下就知道索引是否一致。
