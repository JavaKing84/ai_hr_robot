# 项目创新点声明（Innovation Statement）

> 用途：比赛答辩 / 项目说明书。
> 本声明严格遵循三原则：**① 如实声明通用组件复用；② 精准定位核心创新；③ 不夸大、守住底线。**
> 事实基准：`README §9 Borrowed Implementations`（15 项，star 数与许可证均于 2026-11-03 经 GitHub API 实读核验，非文档旧数字）。

---

## 〇、一句话结论

本项目**没有发明任何新模型、新算法或新架构**。它的全部"创新"集中在**业务编排层**——把「邮件」与「飞书」两种异构沟通介质，绑定到**同一份候选人 / 职位上下文**，并汇入**一条统一的指令解析链路**。这是一项**「多源输入融合 + 流程编排」**的工程创新，**而非算法创新**。

---

## 一、通用组件复用（如实声明）

简历文本提取、职位匹配打分、去重与状态枚举、定时调度、飞书接入、邮件线程、LLM 结构化抽取等底层能力，均**借鉴 / 复用了成熟开源方案**（详见 `README §9`，共 15 项；GPL / AGPL / 非标准许可项目**只借鉴设计、零代码复制**，并明确许可证隔离）。

| 能力域 | 复用的成熟开源方案 | 复用方式（均不复制受限代码） |
|---|---|---|
| 简历文本提取与清洗 | Unstructured（Apache-2.0） | 借鉴分区思路，作**首选可缺省依赖**、失败自动降级 |
| 简历–职位匹配与打分 | Resume-Matcher（Apache-2.0） | 借鉴「提取→比对→打分→排序」分层，不复制代码 |
| 重复投递拦截与状态枚举 | frappe/hrms（GPL-3.0） | 仅借鉴业务逻辑，自行实现去重与事件追加（GPL 隔离） |
| 定时任务调度 | apscheduler（MIT） | 直接作为依赖使用（MIT 兼容） |
| 飞书消息 / 事件接入 | larksuite/oapi-sdk-python（MIT） | 官方 SDK 直接依赖，不自行实现签名 / 加密 |
| 飞书 Webhook 路由范式 | Dify-FeiShu-bot（MIT） | 借鉴结构，用 FastAPI 复刻同等范式 |
| 消息通道归一 | AstrBot（AGPL）/ LangBot（Apache-2.0） | 仅借鉴"多渠道 → 内部消息对象"架构思想，零代码复制 |
| 非阻塞邮件发送 | fastapi-mail（MIT） | 借鉴 `aiosmtplib` + 后台任务模式 |
| 邮件线程模型 | sentry（FSL）/ zammad（AGPL）/ open-agent-email（Apache-2.0） | 借鉴线程模型与匹配顺序，零代码复制 |
| 线程重建（JWZ） | python-emailthreads（MIT，已归档） | 重写 60 行最小实现，**不引入依赖** |
| token 化回复路由 | mailin（MIT，Node.js） | 仅借鉴地址别名兜底思路 |
| LLM 结构化抽取 | google/langextract（Apache-2.0） | 借鉴「Schema + source grounding」设计 |

> **这不是"偷懒"，而是工程判断**：把成熟的轮子用于"脏活"（解析、通道、调度、抽取），把团队有限精力集中投在**真正需要定制的编排与融合层**，并严格守住许可证边界。这本身就是产品文档要求"可被复用、可审计"的落地方式。

## 二、核心创新点（精准定位）

> **创新类型界定：业务编排与多源输入融合（Multi-source Input Fusion + Business Orchestration）。**
> **非**算法创新、**非**新架构。
>
> **一句话**：本项目把「邮件」与「飞书」两种异构介质的回复，绑定到**同一份候选人 / 职位上下文**，并汇入**同一条指令解析链路**，全程受安全护栏约束。

拆解为三个**可验证**的子能力：

### 2.1 双介质入口归一（多源输入融合）

- 主管的回复可能来自 **飞书自由文本 / 卡片回调**，也可能来自**在原简历邮件线程上的回复**。
- 两种介质的报文格式、身份体系、送达通道完全不同；本项目把它们统一抽象成内部 `InboundMessage`，再进入**同一个解析 / 编排入口**（`FeedbackService`），**不写两套业务逻辑**。
- **意义**：主管"在哪说都一样"，机器人侧只维护**一套指令语义**。

### 2.2 跨介质上下文绑定（Context Binding）

- **邮件侧**：基于持久化 `Message-ID` + `In-Reply-To` / `References` + 发件人 / token 兜底，把"这条回复"精确绑定到"哪位候选人 / 哪个职位 / 哪一轮通知"；丢头时由 token 别名兜底，**保证线程不断链**。
- **飞书侧**：主管提到的人名必须**接地到本轮已分发的候选人名单**（I-05 姓名接地），未接地即判定"未识别"，**不猜、不发**。
- **意义**：两条介质各自解决"这条消息属于谁"，且都收敛到**同一个候选实体**，供后续统一处理。

### 2.3 统一指令解析 + 安全护栏（Unified Parsing & Guardrails）

- 两条入口汇入**同一套** LLM / 规则抽取（Pydantic schema 一致），输出统一的动作意图（面试名单 + 时间 / 改期 / 放弃 / 确认）。
- **时间只来自主管**：机器人不猜时间、不替主管答应改期；缺姓名或缺时间时**只回消息追问，绝不发错邮件**。
- **意义**：无论走飞书还是邮件，**指令语义、抽取 schema、安全红线完全一致**。

> **为什么这是"编排 / 融合"创新，而非算法创新**：它没有训练任何新模型，也没有提出新的抽取 / 匹配算法；它的贡献在于**把多个既有组件按「双介质 → 同上下文 → 同解析 → 同护栏」的方式组合**，使异构输入在业务层表现为**单一、确定、可审计**的一条链路。

## 三、不夸大（守住底线）

明确声明：

- **不宣称任何算法创新**——没有发明新模型、没有提出新抽取 / 匹配算法、没有改进任何机器学习方法。
- **不宣称新架构**——采用业界标准的分层（`api / service / repository / client / model`）与异步 ORM，均为成熟工程实践。
- **不宣称"全自动无人值守"**——关键决策（时间、改期）始终**以主管为唯一权威**；机器人只做解析、编排与留痕，且对歧义输入**"只追问、不瞎发"**。
- **不夸大覆盖范围**——无真实凭证时走 mock 模式（出站内容全量落库落盘、可逐条审阅）；已知限制已在 `README §11` 与 `docs/known-limitations.md` 如实记录。

> 本项目的价值主张是：**在"无界面"约束下**（界面即对话；仓库由测试强制校验无任何前端文件），用**成熟的组件 + 克制的编排**，**高效实现企业内部招聘流程的自动化**，并把"机器人到底发了什么"做到**可逐条审计**。
