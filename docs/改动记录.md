## 2026-11-13 · 修复 docx/pdf 简历解析成空 + 主管 open_id 填错

**改了什么**

1. `client/resume_parser.py`：文本提取改为「原生库优先、`unstructured` 兜底」（`.docx` → python-docx，`.pdf` → pypdf）。
2. `config/positions.yaml`：三个主管的 `feishu_open_id` 从群 `chat_id`（`oc_...`）改回个人 `open_id`（`ou_...`）。

**为什么**

1. 本机实测 `unstructured.partition()` 解析 docx 会卡住 >120 秒，而解析在 60 秒超时的子进程里跑 → 所有 docx/pdf 简历被强杀成空文本 → 抽取不到学历 → 被硬条件误判淘汰（BOSS 直聘的 docx 附件全军覆没）。
2. `oc_` 开头的是群 chat_id，用它反查主管永远查不到，导致飞书里「认人」失败、面试通知挂不起来（`supervisor_unknown`）。

**改了哪些文件**：`client/resume_parser.py`、`config/positions.yaml`。

**验证**：docx / pdf 解析从 >120s 超时变为 0.14s（403 / 430 字）；四条链路验收从 13/16 提升到 **16/16 通过**；190 个测试仍全绿。

**遗留**：原生库抽不出文本的文件（扫描件）仍会白等一次 60s 兜底超时。

**详见**：`docs/quality/数据库切换PostgreSQL改动说明_20261113.md` 第 5 节

## 2026-11-13 · 飞书机器人接入自然语言（Agent 层）

**改了什么**

1. 新增 `schema/agent.py`（意图枚举 + `AgentPlan` + `AgentFacts`）、`prompt/agent.py`（路由与作答提示词）、`service/agent.py`（`AgentService`：路由 / 事实检索 / 组织语言）。
2. `service/feedback.py`：群里收到文本先过一次意图路由——读类（查名单、解释分数、看统计、读简历、闲聊）由助手作答；写类（排面试、改期、确认、取消、淘汰）仍交给原有确定性代码，模型只提供名单与时间槽位。
3. `client/llm.py`：新增 `complete_text`（自由文本）；`_complete_raw` 统一 litellm 与 httpx 直连两条通道（没装 litellm 也能用 OpenAI 兼容端点）；JSON 解析失败时同供应商重试一次（`max_tokens` 翻倍）；供应商配置支持 `"disable_thinking": true`，对 vLLM + Qwen3 带 `chat_template_kwargs.enable_thinking=false`。
4. `config/settings.py`：`feishu_group_push` 修正为「配了 `FEISHU_CHAT_ID` 或 `FEISHU_WEBHOOK_URL` 任一条即进群」（原实现只认 webhook，只配应用身份会被误判成私聊）；`llm_provider_chain` 保留 `disable_thinking`。
5. `core/deps.py`：`FeedbackService` 注入 `llm`，由它构造 `AgentService`。
6. `.env.example`：补 `HR_FEISHU_OPEN_ID`、`FEISHU_CHAT_ID` 与 `disable_thinking` 的说明。

**为什么**

原来的机器人只认四种固定句式（名单+时间、改期、确认、取消），其他一律回「请按下面格式回复」。主管真正会说的是「这俩都还行，安排后天上午十点半吧」「王耀国为什么才 79 分」「他会 Kubernetes 吗」——正则永远补不完，而且补得越多误判越多。

所以把「理解」交给模型、「执行」留给定代码：模型只输出意图与槽位，姓名还必须落在数据库里真实存在的候选人上（写操作额外限定在可排期名单），发邮件、改状态、留痕全部走原来的路径。模型挂了自动退回旧逻辑，离线仍可用。

**验证**

- 集群实测（真实飞书群）：`查名单` / `解释分数` / `读简历` / `看统计` / `闲聊` / `淘汰某人` 六类自然语言均正确路由并发言；
- 写操作实测：`王耀国挺合适的，安排他明天下午三点来面试` → 状态 `dispatched → supervisor_feedback`，生成 1 份待确认通知；回「确认发送」→ `interview_notified`，事件链 `feedback.received → interview.notice_pending_approval → interview.approval_requested → feedback.schedule_applied → interview.notice_sent → interview.approval_confirmed`；
- 稳定性：同一句复合问题（「还剩几个人，王耀国面试定在什么时候」）连测 3 次全部正确，2s 内返回；
- `pytest` 190 个测试全绿。

**遗留**

- 路由依赖模型，同一句话偶尔会被判成 `unknown`（此时退化为原提示，不会误执行写操作）；
- 对话历史按「最近 6 条飞书消息」取，群聊里多人同时说话时上下文会混；
- 问「简历里有没有 X」只截前 2500 字，长简历后半段搜不到。

**详见**：`docs/guide/飞书自然语言助手.md`

## 2026-11-13 模型供应商切到 DeepSeek 官方 + 支持「改期」写操作

**改了什么**

1. `.env`：`LLM_PROVIDERS` 从学院端点（`202.204.64.234` vLLM）换成 DeepSeek 官方，主用 `deepseek-flash`、降级 `deepseek-v4-pro`，`api_base=https://api.deepseek.com/v1`。
2. `service/feedback.py::_handle_schedule`：可排期名单从「`dispatched` / `supervisor_feedback`」扩到「+ `interview_notified` / `reschedule_pending`」。
3. `service/feedback.py` 主流程：`RESCHEDULE` 意图也复用路由阶段已抽好的槽位（原来只有 `SCHEDULE` 复用，改期会多调一次模型）。
4. 事件留痕：已通知的候选人重排时，`feedback.received` 的 `detail.reschedule=true`、`note="主管改期"`。
5. `.env.example`：模型 ID 说明改为「先 `GET /models` 查真实 ID」，示例换成 `deepseek-flash` / `deepseek-v4-pro`。

**为什么**

- **换 DeepSeek**：学院端点是内部测试机，把简历正文发过去没有数据边界；DeepSeek 官方国内直连、1.5s 级返回，且 `deepseek-flash` 支持 1M 上下文，长简历问答不再撞 2500 字截断之外的上限压力。
- **补改期**：主管说「王耀国改到 11月15日上午十点吧」，路由正确识别成 `reschedule`，但执行时这个人不在名单里（已是 `interview_notified`），最终回了一段「请按格式回复」。这是换模型后才暴露的口径不一致——`_SCHEDULABLE_STATUSES` 认 `interview_notified`，而 `_handle_schedule` 内部又把它筛掉了。

**验证**

- DeepSeek 直连：`GET /models` 200，返回 `deepseek-flash`、`deepseek-v4-pro`；`complete_json` 1.5s 返回合法 JSON，`complete_text` 1.8s；
- 读类四问（名单/解释分数/面试时间/统计）全部正确，2.4–3.1s；
- 改期实测：`王耀国改到11月15日上午十点吧` → `intent=reschedule, names=[王耀国], time_text=11月15日上午十点` → 状态 `interview_notified → interview_pending_confirm`，`interview_time` 落 2026-11-15 10:00（东八区），生成 1 份待确认通知 + `interview.approval_requested` 请示，一封都没真发；
- `pytest` 190 个测试全绿。

**遗留**

- 「给还没派发的候选人排期」仍不支持：`screened_passed` 的人不在主管名单里，机器人会回「本轮没有待反馈的候选人」。这是产品口径（先由 HR 派发再谈面试），不是 bug；要放宽得先定「主管能否跳过派发直接约面」。
- 模型 ID 随时会变，`.env` 里写死两个 ID。补充实测（2026-11-13）：`/models` 只列 `deepseek-flash` 与 `deepseek-v4-pro`，而 `deepseek-chat` / `deepseek-reasoner` 虽未列出仍返回 200，属兼容别名——所以「不在列表里」不等于「不可用」，但新接入应按列表配。

## 2026-11-14 · 排期回执合并成一条 + 关掉二次确认闸门

**改了什么**

1. `interview_notice_require_confirm` 默认值由 `True` 改为 `False`：主管在群里已经点明「通知谁、什么时间」，系统不再回问「请确认全发 / 确认 1,3 / 取消」——那是让主管把同一件事说第二遍。防误发改由邮件通道自身保证（幂等 Message-ID、`MAIL_MODE=mock`、失败不推进状态）。
2. 新增 `config/templates/feishu_schedule_summary.md` 与 `NotificationService.send_schedule_summary()`：把「安排了谁、各自什么时间、地点在哪、谁没安排上」压进**一条**消息，取代原来按岗位各发一条 `feishu_receipt.md`。
3. `FeedbackService._handle_schedule()` 重写回执段：时间逐人取 `candidate.interview_time`，不再拿第一条候选人的时间套给整批（之前周涛的「今天 15:00」被写成「11-18 14:00」）。
4. `_explain_unschedulable` 拆成 `_unschedulable_pairs`（结构化）与 `_format_unschedulable`（拼段落），排不了的人并进同一条回执的失败段，不再单独补发第二条消息。
5. `_names_mentioned` 新增 `_unknown_names_beside()`：主管写「【周涛，张三】」时，模型只抽出周涛，张三会彻底消失；改为把**与已识别人名并列、但库里查不到**的词也带出来，回一句「张三我这边没有这个人」。带停用词与动词/介词过滤，避免把「下午三点」「请通知」当成人名。

**为什么**

- 截图实证：主管三条消息 → 机器人回两条「2 份待确认」「3 份待确认」，且三条都是同一个时间；同一个人被要求确认两遍，还看到错误的面试时间。
- 「一句话对应一条回执」是主管的心智模型；拆成多条后，他会以为系统要他说两次话，且分不清哪条是结论。

**验证**

- `208 passed in 62.01s`（新增 `test_schedule_reply_is_single_message`、`test_unknown_name_reported_in_same_receipt`）。
- 新增断言直接钉死行为：回执条数 == 1、正文含「地点：」、不含「待确认」「确认 1,3」；库里没有的人名必须出现在回执里并说明原因。

**改了哪些文件**

`config/settings.py`、`config/templates/feishu_schedule_summary.md`（新增）、
`service/feedback.py`、`service/notification.py`、`tests/test_hardening.py`、
`tests/test_workflow.py`、`.env`、`.env.example`、`.gitignore`、本文件。

## 2026-11-14 · 演练期关闭真实发信（MAIL_MODE: live → mock）

**改了什么**

1. `.env` 的 `MAIL_MODE` 由 `live` 改为 `mock`，并把三档取值（`mock` / `live` / `off`）各自的行为写进注释，避免下一个人再改回去。
2. 注释里明确标注：`mock` 是**收发一起切**——出站只写 `var/outbox/mail/*.eml`，入站也不再拉 163 IMAP，改读 `var/mock_inbox/*.eml`。

**为什么**

- 演练/验收期不该给真实候选人发面试通知邮件。此前 `MAIL_MODE=live`，只要跑一轮闭环，面试通知就会通过 SMTP 真的投出去，且投递后不可撤回。
- 代码层已有区分（`service/feedback.py` 按 `mail_live` 给出三种不同文案，不会把「生成了草稿」说成「已发送」），但配置没切过去，等于防御只做了一半。

**验证**

- `Settings().mail_mode` 实测返回 `mock`。
- `client/mailbox.py:218` 的 `poll_inbox` 在 `mail_live=False` 时走 `_mock_poll()`，只读本地目录，不发起 IMAP 连接；`send()` 分支在 `mail_mode != "live"` 时写 `.eml` 到 `var/outbox/mail/`，不发起 SMTP 连接。

**副作用（必须知道）**

`MAIL_MODE` 是单一开关，管「收 + 发」两端。改成 `mock` 后，**真实投递到 163 邮箱的简历也不会被自动收取**，需要把 `.eml` 放进 `var/mock_inbox/` 模拟投递。
如果演练需要「真收假发」，就需要再拆一个只控制出站的开关（例如 `MAIL_SEND_MODE`），当前尚未做。

**改了哪些文件**

`.env`、本文件。

| 单独「确认」，无待发面试通知 | 归岗位草稿 |
| 带时间表达的（周三 14:00） | 一律当「安排面试」，不当成对通知的答复 |

### 三个 bug 的实际后果

1. **`In-Reply-To` 永远匹配不上（bug①）**
   发信存的根是 `<7c4d...@163.com>`，收信解析出来是 `7c4d...@163.com`。
   `find_by_any_message_id` 拿后者去比前者，永远不等。
   所以「主管在原邮件上回复」实际一直退化到「按发件人邮箱认人」，
   而发件人那条又因为 `supervisors` 表只剩一位主管而失败（bug②）。
   两个 bug 叠加，这条验收项等于没生效——但表面上一切正常，邮件也"处理了"，只是走错了路。
2. **认人丢信（bug②）**
   `supervisors.feishu_open_id` 是唯一索引 ✅，但三位主管共用同一个飞书号（都是 HR 本人），
   同步时命中同一行，`name/department/email` 被最后一位覆盖。张伟、李娜从自己邮箱回复，
   线程明明命中了，进 `feedback.handle` 又判「不是已登记的主管」→ `supervisor_unknown` → 静默丢弃。
   现在按职位配置兜底，查得到人。
3. **自投回流（bug③，真机才发现的）**
   演示环境里主管邮箱就是 HR 邮箱（`18786112948@163.com`），简历包发出去会绕回同一个 INBOX。
   修之前它被判成「主管说了句话」，机器人自问自答一次（飞书还多了一条莫名其妙的回答），
   并给同一个 Message-ID 重复登记了一条线程。
   现在：`messages` 里能查到「这封是我们自己发出的」就直接忽略。

### 带附件的回信怎么处理

主管点「转发」、或在回复里又拖进一份简历时，回信会带附件。判定顺序改成：

```
先看这封是不是挂在「简历包 / 确认请示」线程上、且带 In-Reply-To
  ↓ 是 → 按主管指令处理（即使带附件）
  ↓ 不是 → 走原来的「带附件 = 新简历投递」
```

只放行这一种情况，2026-11-12 修过的「平台共用发件人吞简历」那个 bug 不会被放回来
（那条路径上不可能出现机器人发出去的 Message-ID），有专门的反向测试钉着。
